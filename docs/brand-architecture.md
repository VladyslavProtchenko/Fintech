# Генератор платформ — архитектура и методология

## Главная идея

Мы строим фабрику финтех-продуктов. Одно описание бизнеса на входе — полноценный работающий сайт с платёжным функционалом на выходе.

Каждая платформа выглядит и ведёт себя как самостоятельный продукт с уникальным брендом, дизайном, языком общения и технической начинкой. Но внутри все они работают на одном платёжном ядре.

Генерация происходит автоматически через систему специализированных агентов — скиллов. Никакого ручного кода, никаких шаблонов. Каждый сайт создаётся с нуля.

---

## Что получается на выходе

Каждая платформа — это пара из двух приложений:

- **Бекенд** — NestJS сервер с REST API и Swagger документацией
- **Фронтенд** — Next.js сайт с лендингом и личным кабинетом

Оба приложения упакованы в Docker контейнеры и запускаются по адресу `http://<slug>.localhost`. Caddy автоматически роутит трафик: `/api/*` идёт на бекенд, всё остальное — на фронтенд.

Пользователь получает две ссылки:
- `http://<slug>.localhost` — сам сайт
- `http://<slug>.localhost/api/docs` — Swagger для работы с API

## Технологический стек

### Платёжное ядро (payment-service)

Единственный сервис который касается денег. Хранит кошельки, балансы, транзакции. Все платформы работают с ним через payment-sdk — никто не лезет в базу напрямую.

Ключевые свойства:
- все операции с балансом атомарны (Prisma транзакции)
- idempotency keys на каждую операцию (защита от дублей)
- нехватка средств — 422 ошибка
- межсервисная авторизация через x-api-key заголовок

### Shared-пакеты

Общая логика которая не дублируется между платформами:

- **payment-sdk** — HTTP-клиент к payment-service. Методы: создать клиента, пополнить, перевести, история
- **shared-auth** — JWT авторизация, guard, декоратор @CurrentUser(), хэширование паролей
- **shared-config** — базовый класс для валидации ENV переменных при старте
- **shared-prisma** — PrismaService с правильным адаптером для PostgreSQL
- **shared-health** — /health эндпоинт через Terminus
- **shared-errors** — GlobalExceptionFilter, типизированные ошибки
- **shared-logger** — структурированные JSON логи
- **shared-redis** — createRedisModule(), нужен для сервисов с очередями

### Бекенд каждой платформы (NestJS)

Это тонкий слой между пользователем и payment-service. Что он делает:
- регистрирует и авторизует пользователей (JWT)
- проксирует платёжные операции через payment-sdk
- маппирует технические walletId на человекочитаемые имена
- применяет ленивое подключение — платёжный аккаунт создаётся при первом обращении к кошельку, не при регистрации

Уникально для каждой платформы:
- пути эндпоинтов (`/wallet/*`, `/account/*`, `/balance/*` и т.д.)
- формат ошибок (`{ok, reason}`, `{message, code, statusCode}`, `{error.type, error.detail}`)
- названия полей в запросах (`amount`, `sum`, `value`)
- название модуля для кошелька

### Фронтенд каждой платформы (Next.js)

Next.js App Router с Server Components и Server Actions. Никакого client-side fetch к API.

Структура страниц:
- **Лендинг** — уникальный контент про конкретный бизнес, не шаблон
- **Логин / Регистрация** — формы с useActionState
- **Дашборд** — баланс + последние транзакции
- **Пополнение** — форма, после успеха — редирект на дашборд
- **Отправка** — мультишаговая форма: поиск получателя → сумма → подтверждение
- **История** — пагинация через URL searchParams

Уникально для каждой платформы:
- цвета и шрифты (Google Fonts)
- расположение элементов (боковая панель слева/справа, верхнее меню, минималистичный)
- стиль отображения транзакций (таблица, карточки, таймлайн)
- терминология (Recharge/Top Up/Load Balance, Send/Transfer/Wire и т.д.)
- стиль главной страницы (hero по центру, split, gradient, minimal)

### Инфраструктура

- **PostgreSQL** — один инстанс, у каждой платформы своя база (`<slug>_db`)
- **Docker + Caddy** — Caddy читает labels контейнеров и автоматически создаёт роутинг для `<slug>.localhost`
- **platform-manager** — NestJS сервис который принимает команду "задеплой платформу", собирает образы и запускает контейнеры

## Процесс создания — 5 шагов

Весь процесс автоматизирован. Оркестратор `create-client-platform` запускает пять скиллов последовательно без остановок.

### Шаг 1 — Исследование и стратегия (platform-research)

Получает описание бизнеса. Делает три вещи:

- Идёт в интернет и изучает конкурентов в этой индустрии — их сайты, цвета, контент, структуру
- Читает реестр уже созданных платформ — какие порты заняты, какие цвета использованы, какие стили эндпоинтов есть
- Читает секреты из реальных файлов — PAYMENT_API_KEY из payment-service, формат DATABASE_URL из существующей платформы

На выходе — стратегия бренда: slug, порты, цвет (hue), шрифты, лейаут, терминология, стиль бекенда, контент для лендинга. Всё это остаётся в контексте для следующих шагов.

### Шаг 2 — Дизайн айдентики (platform-design)

Получает стратегию из контекста. Создаёт визуальную айдентику:

- Придумывает 3 концепции иконки, выбирает лучшую
- Генерирует SVG логотип (иконка + название) и SVG favicon (только иконка)
- Иконка должна работать на размере 16px — никаких тонких линий и мелких деталей
- Формирует дизайн-токены: палитра цветов (50 до 950), шрифты, радиусы

Всё это остаётся в контексте.

### Шаг 3 — Генерация бекенда (platform-api)

Читает реальный код shared-пакетов и референсную реализацию перед генерацией. Создаёт полный NestJS проект в `platforms/<slug>/api/`:

- package.json с workspace зависимостями
- tsconfig с правильными путями к dist/ пакетов
- Prisma схема с User моделью
- Модули: auth, кошелёк, поиск пользователей, health
- GlobalExceptionFilter с уникальным форматом ошибок
- Dockerfile для продакшна (multi-stage build)
- .env с реальными значениями (скопированными из существующих сервисов)

Применяет все правила: ленивое подключение, атомарные операции, правильная обработка ошибок payment-service.

### Шаг 4 — Генерация фронтенда (platform-web)

**Сначала читает сгенерированный бекенд** — контроллеры и DTOs — чтобы знать точные пути и названия полей. Это предотвращает рассинхрон между бекендом и фронтендом.

Создаёт полный Next.js проект в `platforms/<slug>/web/`:

- globals.css с Tailwind 4 @theme (цвета и шрифты из стратегии)
- lib/api.ts — серверный fetch wrapper с cookies(), ApiError, поддержкой query параметров
- Server Actions для auth, платёжных операций, поиска пользователей
- Все страницы: лендинг, логин, регистрация, дашборд, пополнение, отправка, история
- UI компоненты в стиле платформы
- Dockerfile и .dockerignore

Лендинг не шаблонный — содержит реальный контент про бизнес, написанный на основе исследования рынка из шага 1.

### Шаг 5 — Деплой (platform-deploy)

Финальный обязательный шаг. Задача не считается выполненной пока сайт не запущен.

- Создаёт docker-compose.yml с Caddy labels
- Добавляет `CREATE DATABASE <slug>_db;` в общий init.sql
- Добавляет запись в реестр платформ
- Устанавливает зависимости, собирает shared-пакеты, генерирует Prisma клиент
- Проверяет что TypeScript компилируется без ошибок
- Деплоит через platform-manager (или напрямую через docker compose)
- Проверяет health эндпоинты — API, главная страница, Swagger

## Тестирование (platform-test)

Отдельный скилл, запускается по запросу после деплоя.

Перед тестированием читает реальные контроллеры и DTOs платформы — чтобы знать точные пути и поля. Никаких догадок.

11 тестов:
- health эндпоинт
- Swagger доступен
- регистрация двух пользователей
- логин
- баланс (lazy provisioning — кошелёк создаётся при первом запросе)
- пополнение на $500
- перевод $100 между пользователями
- перевод самому себе — должна быть ошибка
- перевод при нехватке средств — должна быть ошибка
- история транзакций
- фронтенд страницы отвечают

Результат — список с [OK], [FAIL], [SKIP]. При падении — полный запрос и ответ.

## Что гарантирует уникальность

Перед каждой генерацией скилл `platform-research` проверяет реестр и гарантирует:

- **Порты** — каждая платформа получает свою пару: API и Web
- **Цвет** — hue нового цвета должен отличаться минимум на 30 градусов от всех существующих
- **Шрифты** — каждая пара шрифтов уникальна
- **Лейаут** — варианты чередуются (top-nav, sidebar-left, sidebar-right, minimal)
- **Стиль эндпоинтов** — пути, префиксы, версии отличаются
- **Формат ошибок** — свой уникальный для каждой платформы
- **Терминология** — слова для "пополнить", "перевести", "баланс" уникальны

---

## Что остаётся одинаковым

- **Платёжное ядро** — payment-service и payment-sdk. Это не меняется никогда
- **Базовые функции** — баланс, пополнение, перевод, история. Стандарт индустрии
- **Паттерн авторизации** — JWT, httpOnly куки через shared-auth
- **Ленивое подключение** — платёжный аккаунт создаётся при первом запросе к кошельку
- **Инфраструктура** — Docker, Caddy, PostgreSQL, одна сеть

## Реестр платформ

Файл `docs/client-registry.md` — единый источник правды. Каждая платформа добавляет строку при деплое. Следующий скилл читает этот файл перед генерацией.

Текущие платформы:
- **greenapple** — 3010/3011 — зелёный (120°) — Nunito+Inter — top-nav — японский яблочный бизнес
- **orange** — 3012/3013 — оранжевый (30°) — Poppins+DM Sans — sidebar-left — испанские апельсины
- **cactus** — 3014/3015 — бирюзовый (150°) — Outfit+Inter — sidebar-right — корпоративный
- **apricot** — 3016/3017 — синий (215°) — Montserrat+Nunito Sans — top-nav minimal — Абрикос UA
- **cherry** — 3018/3019 — вишнёвый (345°) — M PLUS Rounded 1c+Inter — top-nav — японская газировка

## Как добавить новую платформу

Один запрос Claude Code:

> "создай платформу [описание бизнеса]"

Скилл `create-client-platform` запускает весь пайплайн сам.
Через ~15 минут получаешь два адреса: сайт и Swagger.
